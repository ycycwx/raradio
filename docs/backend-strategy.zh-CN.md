# 后端选择与扩展路线

[English](backend-strategy.md) | 简体中文

上游文档核对日期：2026-09-12。本文区分 raradio 已实现的后端与候选方案；安装和运行命令见 [使用手册](handbook.zh-CN.md)，运行证据及限制见 [验证记录](verification.zh-CN.md)。

CLI 同类工具的实际选择与可借鉴点见 [同类项目调研](reference-projects.zh-CN.md)。其中区分了通用 API、Ollama 适配器、规则与 BookNLP 人物分析，作为后续接口设计的参考。

## 当前后端

raradio 当前提供 Ollama 文本分析与 MLX 语音合成。llama.cpp 是待评估的扩展方向，尚未接入。更换默认后端前，需要分别评测文本分析和语音生成。单人朗读可以直接跳过文本大模型。

后端选择需要依据具体接口、模型和版本的运行结果。社区规模和硬件覆盖可以帮助筛选候选，但不能直接证明 raradio 的语音质量、生成速度或长任务可靠性。

raradio 有两个不同任务，可以独立更换引擎：

```text
原始 TXT → 切章和切段 → 角色/情绪标注 → 已确认角色与声音 → 逐段语音 → QA → 章节导出
                         ↑                         ↑
              文本分析器，可不用 LLM             TTS 后端
              当前：Ollama / rules /             当前：MLX / tone
                    single-voice                （tone 仅诊断）
              候选：llama-server                候选：llama-tts
```

文本分析与语音合成使用不同的模型接口。语音步骤需要受后端支持的 TTS 模型及音频处理组件；文本模型不能直接替代它们。

## 路线与状态

| 路线 | 对社区、安装和定制的意义 | raradio 当前状态 |
| --- | --- | --- |
| Ollama 文本分析 + MLX TTS | 使用 Ollama 管理文本模型，通过 MLX-Audio 的 Python API 合成语音；当前语音路径面向 Apple Silicon Mac | 已实现；短样本运行证据见 [验证记录](verification.zh-CN.md)，尚无整本书质量结论 |
| llama-server 文本分析 + MLX TTS | 让熟悉 llama.cpp 的用户复用自己的服务和推理参数；保持语音流程不变 | 尚未实现文本适配器 |
| llama-server 文本分析 + llama-tts 语音 | 评估其他设备上的语音运行路径；需要包装语音进程、音频契约和安装方式 | raradio 尚未接入；上游提供语音生成演示工具 |

`llama-server` 提供 OpenAI 兼容聊天接口和受 schema 约束的 JSON 输出。[llama-server 文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)。raradio 的 Ollama 分析器使用 `/api/chat` 及其 `format`、`think`、`keep_alive` 参数，需要独立适配器才能接入其他协议；只改 `--ollama-url` 不足以完成切换。语音合成还需单独适配，聊天接口的兼容性不代表语音接口兼容。

## llama.cpp 语音候选

在上述核对日期，官方 `llama-tts` 文档提供了使用 `libmtmd` 运行 Qwen3-TTS Base 的示例，并提供语言和参考录音参数。以下是上游工具的独立命令，不是 raradio 命令，也不代表已完成 raradio 集成验证。[官方 TTS 用法](https://github.com/ggml-org/llama.cpp/blob/master/tools/tts/README.md)。

```sh
llama-tts \
  -hf ggml-org/Qwen3-TTS-12Hz-1.7B-Base-GGUF \
  --tts-lang zh \
  --tts-speaker-file reference.wav \
  -p "雨停了，明天再来这里。" \
  --output cloned.wav
```

准备模型文件、配套组件和构建时，应使用所选 llama.cpp 版本的官方说明。raradio 的现有 MLX 安装过程不会安装 `llama-tts`，也不会准备它所需的 GGUF 文件。该路径尚无 raradio 的真实生成、质量或恢复验证记录。

接入前还需核对参考录音、转录和情绪参数的语义。Qwen 官方区分音频加转录的克隆与仅使用说话人特征的模式，并提示后者可能影响克隆质量。[Qwen3-TTS 克隆说明](https://github.com/QwenLM/Qwen3-TTS#voice-clone)。raradio 的 MLX 后端分别提供 `icl` 与 `xvector` 配置；比较候选后端时，需要明确各自实际使用的模式。

## 已有扩展边界

raradio 已把人物身份和声音配置分开。可以编辑 JSON，为不同角色选择预设声音或参考录音。修改声音配置时，使用该配置的片段会失效；来源文本、人工归属修正和不受影响的音频继续保留。多个角色共用一个声音配置时，它们都会受该配置变更影响。

开发者层面已有内部边界，但**还没有发布第三方插件 SDK，也没有安装后自动发现插件的机制**：

| 边界 | 已有接口与职责 | 仍需实现的扩展能力 |
| --- | --- | --- |
| 文本分析 | `analyze(segments, characters) → AnalysisResult`；项目验证原文不变并保存标注 | llama-server 适配器、分析器注册、独立的服务配置 |
| 语音合成 | `Backend.synthesize(text, voice, emotion, output)`；`version` 参与缓存 | 后端注册、能力描述、插件选项验证、llama-tts 适配器 |
| 质量检查 | 当前固定的 WAV 结构与波形检查 | ASR、音色检查及检查器扩展接口 |

当前 CLI 分析器选项及 TTS 工厂仍是内置名单。新增 Python 后端还需要修改注册位置；在 JSON 写一个新 `backend` 名字不会自动加载外部包。`VoiceProfile` 的现有字段也不是任意插件参数容器，未知字段会被拒绝。

后续插件接口应让适配器负责把输入变成标注或 WAV，由核心统一处理源文本约束、持久化、缓存、有限重试、人工复核和导出。候选设计是显式选择、按需加载的 Python 包注册机制；单个插件应声明自己的依赖、版本和能力，例如是否支持参考录音、是否需要转录、能否接收情绪指令、输出采样格式。不支持的参数应明确报错。

插件可调用 HTTP 服务或外部二进制，无需为每个插件维护 C++ 分叉。文本适配器应把请求格式、JSON 响应和服务错误藏在边界内；命令行 TTS 适配器应负责参数列表、超时、取消、独立临时目录、输出完整性和清理。仅停止自己启动的进程；外部共享服务的加载与释放要遵守其接口和用户配置。

## 后续实施顺序

1. **补全验证基线。** 本仓库提供 `uv.lock`、无模型流程和短样场景。后续真实模型验证应记录引擎版本、权重版本、配置及结果；模型同名不意味着文件未变。
2. **增加第二个文本后端。** 将 provider 配置与项目业务分离，先接 llama-server，以同一组标注契约测试验证输入保真、非法 JSON、超时和上下文边界。用户能通过配置选择后端后，再谈更换默认值。
3. **验证第二个语音后端。** 固定 llama.cpp 构建和 GGUF 版本，先验证少量中文样本、克隆、截断检测与中断恢复，再对接 raradio。初期标明实验性质，不承诺与 MLX 的 ICL、情绪或速度配置完全相同。
4. **用第二个实现校准插件接口。** 提取真正共有的配置和生命周期，提供最小示例插件、契约测试、错误约定及能力表。依赖按后端安装，核心不强制用户安装全部引擎。
5. **记录后端支持范围。** 新增后端时同步更新平台说明、依赖、引擎与模型许可链接、最小示例和故障报告要求。公开示例应使用可再分发的文本和媒体，运行数据及模型权重不纳入源码仓库。

这些步骤尚未全部实现，也没有承诺发布时间。第三方扩展接口应在第二个实现与契约测试形成后再确定。

## 什么证据足以改变默认后端

文本比较应尽量保持模型家族、权重版本、量化等级、聊天模板、上下文和采样设置一致，记录冷启动、预热后耗时、峰值内存、人物归属准确率、JSON 失败率、人工复核量与长任务恢复表现。量化格式或实现无法完全对齐时，应明确差异，不能将全部差异归因于引擎。

语音应单独比较：相同文字与参考录音的漏读/重复、音色与韵律、生成耗时相对音频时长、内存、失败率及取消后续跑。先盲听短样，再验证整章，之后才做整本书。社区规模和项目数量只能提供背景，不能替代这组实测结果。

默认后端应由评测结果决定。新适配器的兼容目标是继续使用已有角色表、人工修正和原文项目；更换语音后端会使相关音频缓存重新生成。
